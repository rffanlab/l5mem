# L5 扩容设计：数据量大了以后怎么办

结论先说：**SQLite 本身不是瓶颈，瓶颈在「检索要处理的命中数随库变大而线性增长」的那几步。**
把这几步改成只跟「最新的一段」或「一小部分重要条目」有关，单机单文件可以撑到几百万条、检索仍在 10 ms 量级。
真正需要换架构（分库、换引擎）的门槛在 500 万条以上或者多台机器同时大量写入，对一组机器人的记忆库来说要很多年才会碰到。

## 1. 会有多大

| 来源 | 估算 |
|---|---|
| InfoCollector | 日报事实约 10 条/天、沉思 5–15 条/天、文章判断几条/天 → 一年约 1 万条 |
| 冷启动补录 | 一次性几百条 |
| Hermes 等机器人 | 每个机器人每天几十到上百条：10 个机器人一年 10–40 万条 |
| 合计 | 第一年 10 万–50 万条；三年内到 100 万条是可能的 |

单条平均 300–500 字，含双索引后约 1.3 KB/条：100 万条 ≈ 1.3 GB 数据库文件，158 的磁盘完全不是问题。

## 2. 实测：变慢在哪里

同一台开发容器（2 核）、`l5bench` 同一份压力语料（任何 2 字词都会命中 20%–40% 的条目，比真实库「挤」得多），p50，
左边是 v2.0、右边是本次 v2.1：

| 规模 | 2 字高频词 | 2 字稀有词 | 4 字短语 | 主题前缀 | 标签点查 | 写入 条/秒 |
|---|---|---|---|---|---|---|
| 20 万 | 8.65 → **3.97** ms | 2.18 → 1.71 ms | 2.72 → 1.83 ms | 8.33 → **2.31** ms | 2.18 → 2.94 ms | 6311 → 6375 |
| 50 万 | 15.62 → **7.70** ms | 2.20 → 2.77 ms | 5.05 → 3.24 ms | 18.76 → **4.29** ms | 3.01 → 2.62 ms | 5596 → 6069 |
| 100 万 | 35.69 → **9.37** ms | 3.49 → 4.41 ms | 7.62 → 5.06 ms | 26.58 → **4.27** ms | 3.24 → 3.31 ms | 5264 → 5348 |

recall@5 全部 1.00；并发 4 读写（400 写 + 1600 读）0 错误。几毫秒级的小幅波动是 2 核容器上的噪声。
内存：20 万条时进程堆约 29 MB（候选元数据常驻），100 万条约 150 MB；数据库文件约 1.4 KB/条。

把 20 万条时一次「数据中心」检索拆开看（改前 35 ms）：

| 步骤 | 耗时 | 为什么慢 |
|---|---|---|
| 补旧的重要条目（原则/决策/判断/教训） | 每路 10–11 ms | `id IN (全部命中)` 要把几万条命中逐条按类型筛一遍，和命中数成正比 |
| 二元组多词求交 + 窗口内 bm25 | 约 13 ms | 3 个高频二元组的倒排表求交，要走完几万条 |
| 主题前缀 | 3–8 ms | 前缀很泛时，要把所有匹配的主题回表取时间再排序 |
| 各路串行 | 加总 | 五路一路一路跑，延迟是各路之和 |
| 元数据、打分、取正文、邻近度 | 合计约 1 ms | 和规模基本无关（只处理前几百个候选） |

**SQLite 的写入（单写者，6000–8000 条/秒）、点查、事务都远没到上限。** 慢的全是「跟命中数成正比」的步骤。

## 3. 已经做了（v2.1，向后兼容，老库第一次打开时自动迁移）

| 优化 | 做法 | 效果（20 万条，剖析测试里的单步/单次检索） |
|---|---|---|
| 重要条目小索引 | 原则/决策/判断/教训另进一张 `fts_imp`（同样的二元组文本）。高频词只在最新一段里排序时，窗口之外的重要条目从小索引按新到旧取 100 条 | 这一步 10.3 ms → **0.13 ms** |
| 各路并行 | 二元组、三元组、主题、标签几路用 goroutine 同时查（WAL 下读不互相阻塞） | 延迟 ≈ 最慢一路 |
| 长词只走三元组 | 查询词都 ≥3 字时，三元组（原文连续出现）一路就能找全，不再在二元组上做多词求交；三元组一条都没找到再退回二元组 | 「数据中心」35 ms → **6.3 ms** |
| 主题覆盖索引 + 有界扫描 | 索引改成 `(topic, created_epoch)`，不回表；前缀太泛时只看按主题排的前 1000 条再按时间排 | 主题前缀 8.3 ms → **2.3 ms** |
| 元数据内存瘦身 | 类型、生命周期这种只有几种取值的字符串共用一份；按条数预分配 | 百万条省几十 MB、启动更快 |

检索结果的排序和以前一致（只是更快）：所有已有测试和 recall@5 = 1.00 不变。

### 心头和新连接的开销

- 写入时只在内存里记一笔（标签 × 天），随访问计数每 5 分钟回写到 `tag_daily`（每个标签每天一行），读路径不碰库
- `mind`：扫最近 365 天的 `tag_daily` 在内存里算激活度；20 万条、3800 个活跃标签（约 140 万行，比真实库密得多）时约 0.4 秒。
  每天只被沉思和巡检各调一次，不做缓存；如果以后有高频调用，改成每天巡检时算好存一份
- `links`：只看窗口内的条目（默认 7 天），每对候选查一次「以前有没有一起出现过」（走 `entry_tags` 主键）；20 万条时约 0.15 秒
- 标签文档数（判断大词用）缓存 5 分钟

## 4. 下一步：按触发条件分级做

不提前做，等指标到了再做。每日巡检会把条目数、检索 p95 写进报告，到了门槛在报告里提醒。

### 一级：50 万条以上，或检索 p95 > 20 ms

1. **冷热分段（最重要的一步）**
   - 全文索引按时间分两段：`fts_hot`（最近 180 天）和 `fts_cold`（更早）。重要条目的小索引不分段
   - 默认只查热段 + 重要条目小索引；热段命中不够 `limit`、或者带了 `--until` / `--history` 时，再查冷段
   - 每天巡检时把超龄的条目从热段挪到冷段（删一行、插一行，增量很小）
   - 效果：高频词的工作量只跟「最近半年写了多少」有关，跟库总大小无关。新鲜度本来就占 25% 权重，
     冷段的事实很少能排进前 8，除非它是原则/决策/判断/教训——而这些在小索引里，永远查得到
2. **失效条目移出主索引**
   - 被取代、被撤回的条目从主索引删掉，放进 `fts_hist`，只有 `--history` 时才查
   - 现在它们留在主索引里、每次检索都要被筛掉一遍；取代链越长越浪费
3. **全文索引段合并**
   - FTS5 的倒排表是一段一段追加的，段越多检索越慢。调 `automerge` / `crisismerge`，巡检时在低峰做增量 `merge`（每次限量，不锁太久），
     不做会长时间锁写的全量 `optimize`
4. **备份换快照**
   - 现在的每日备份是整库导出 JSONL：100 万条约 1 GB、要一两分钟。改成 SQLite 在线备份（`VACUUM INTO` 到临时文件再压缩），
     几秒钟、不阻塞读；JSONL 导出降为每周一次（它的价值是跨版本迁移）
5. **按库大小调缓存**
   - `mmap_size` 跟着库文件大小走（上限按机器内存的 1/4），`cache_size` 同理；现在写死 256 MB / 64 MB
6. **元数据改成列式**
   - 内存里的候选元数据从「每条一个对象 + map」改成按列的数组（id、时间、类型编号……），主题前缀筛选改走索引。
     100 万条时从约 150 MB 降到约 40 MB，启动加载从秒级降到亚秒

现在 100 万条时高频词 p50 已经是 9.4 ms；做完一级，预期 100 万–500 万条时保持在 10 ms 以内，内存 < 200 MB。

### 二级：500 万条以上，或多台机器同时大量写

1. **按领域分库**
   - 每个调用方/领域一个 SQLite 文件（`infocollector.db`、`hermes.db`、`shared.db`……），同一个进程管理
   - 写入各写各的，没有锁竞争；检索并行扇出到相关的几个库，用 RRF 合并（现在的融合本来就是 RRF，天然支持）
   - 同义词组、重要条目放在共享库
2. **只在一级用尽后才考虑换引擎**：专用的段式倒排引擎（例如 Tantivy）在亿级才有明显优势，
   代价是失去「一个文件就是全部数据、拷走就能用」的运维简单。

### 和规模无关、但值得补的：语义检索

现在全是字面匹配：「降价」查不到「价格下调」。可以加一路向量检索：

- 嵌入模型跑在 158 本地（Ollama / ComfyUI 同机的小模型，384 维）
- 向量 int8 量化：100 万条 × 384 字节 ≈ 384 MB；先按冷热分段只在热段 + 重要条目上建，规模小一个数量级
- 作为第五路进 RRF，不替代字面检索（专有名词、数字、代码还是字面匹配准）

## 5. 不建议做的

- **现在就换 PostgreSQL / Elasticsearch**：吞吐离瓶颈差两个数量级；多一个要运维的服务，158 的内存要分给它；
  失去单文件备份迁移的简单。等二级门槛到了再评估，而且优先分库
- **加机器做读写分离**：记忆库是低写入、低并发的负载，单进程 + WAL 已经足够；复杂度不值得

## 6. 怎么知道该做下一级了

| 指标 | 来源 | 门槛 |
|---|---|---|
| 条目数 | `l5 stats` | 50 万 → 一级；500 万 → 二级 |
| 检索 p95 | 使用日报（`l5 metrics`） | 连续一周 > 20 ms → 一级 |
| 启动时间 | 服务日志 | > 5 秒 → 元数据列式 |
| 每日备份耗时 | 巡检报告 | > 60 秒 → 备份换快照 |
| 写入排队 | 使用日报写入 p95 | > 50 ms → 二级（分库） |

剖析工具：`L5_SCALE=200000 L5_SCALE_DIR=/tmp/l5scale go test -tags sqlite_fts5 -run TestScaleProf -v ./internal/store/`
会造一个指定规模的库，逐条给出每一路、每一步的耗时（库文件留着，下次直接复用）。
